## 1. What the demo is, and is not

A local web page (the existing `scripts/demo/`) where one person chats with v4. It shows, with real numbers:
1. the model answering what it knows, and saying "I will look that up / calculate that for you" and calling one of 9
   tools when it does not or cannot; the tool runs for real and the model answers from the result;
2. short multi-turn conversation (the last 2-3 turns, carried by attention, labelled as such);
3. brains: a small file trained from documents, switched on and off in one click, with a closed-book quiz showing
   base vs brain vs wrong brain; with the brain on, the model stops saying "I will look that up" for that domain;
4. the brain view from 10-04: spike raster, honest energy meter (energy-v2 counting), memory-off replay on the
   key-value recall task the memory was trained for.

NOT in the demo: plain-language long-term memory, more than one tool call per turn, a brain made without weight
training, any hosted or multi-user service, real sending of messages.

## 3. Designs

### D1. Response protocol v2: the model announces the tool (point 1 wording)

```
### Response:
TOOL I will calculate that for you. {"name": "calculator", "arguments": {"expression": "0.17 * 240"}}
```
- The mode word stays first (it is the trained, constrained switch). After `TOOL ` comes ONE fixed sentence per tool,
  then the same canonical JSON as today. The sentence decides the tool; the grammar then forces the matching name, so
  sentence and call can never disagree.
- Sentences (new `"say"` field in `training_data/posttrain/tools.json`, `"version": 2`):
  search "I will look that up for you." | calculator "I will calculate that for you." | unit_convert "I will convert
  that for you." | get_weather "I will check the weather for you." | get_time "I will check the time for you." |
  define "I will look up that word for you." | translate "I will translate that for you." | set_reminder "I will set
  that reminder for you." | send_message "I will send that message for you."
- No data is regenerated: the 14,396 tool records get the sentence when they are formatted.
- Changes (the "four places" of `src/tool_data.py:3`): `tool_data.format_response` (:89) adds the sentence;
  `tool_data.parse_response` (:168) skips text between `TOOL` and the first `{` (accepts v1 and v2);
  `grammar.ToolGrammar._build` (`src/grammar.py:91`) chains `TOOL ` + say + ` {"name": "<that tool>", "arguments": {`
  per offered tool; `scripts/tool_eval.py` gains `say_ok`. `scripts/head_eval.py:69` and `src/train_heads.py:109`
  only call `parse_response`, so they follow. `scripts/gen_teacher_data.py` formats no responses: untouched.
- Selector: config key `tool_proto: 2` (stored in the checkpoint; absent = 1 = byte-identical, so `sft_v4_reh13` and
  v3 checkpoints still evaluate with the old grammar).
- All 9 tools offered at demo time but 2-6 in training: `tool_data.load_tool_jsonl` gets `full_frac` (config
  `sft_tools_full_frac: 0.3`, default 0): for that share of `tool` and `answer` records (hash-chosen, never
  `tool_absent`) the offered list is extended to all 9, shuffled.
- Test: `temp/test_tool_proto2.py` (CPU): every training target is accepted by the v2 grammar; `parse_response`
  round-trips v1 and v2; v1 output is byte-identical with `tool_proto` absent.

### D2. Executors for the 9 tools (point 2)

New `scripts/demo/tools_exec.py`: `run(name, arguments, offline=False) -> {ok, text, source, card}`; `text` is the
short plain-text result the model reads (<= ~80 tokens), `source` is `live` / `offline` / `simulated` and is shown on
the page. Every network call has a 4 s timeout and falls back to the offline path.

| tool | real path | offline path |
|---|---|---|
| calculator | safe evaluator on the Python `ast` (numbers, + - * / ** %, parentheses, sqrt, percent); never `eval` | same |
| unit_convert | own table: length, mass, volume, temperature, speed, area, time, data; unit aliases | same |
| get_time | stdlib `zoneinfo`, plus a city / abbreviation -> zone alias table | same |
| define | – | WordNet through `nltk` (installed; ~30 MB data download) |
| search | Wikipedia REST (search + summary), cached to disk | local pack: first paragraphs of ~50-100k Simple English Wikipedia articles in SQLite FTS5 (in the stdlib, checked) + the brain documents |
| get_weather | Open-Meteo (no key) | last cached reading per city, labelled with its time; otherwise "no network" |
| translate | – | Helsinki-NLP opus-mt models through `transformers` (es, fr, de, it, pt; ~300 MB each, CPU) |
| set_reminder | simulated: stored in `logs/demo_reminders.json`, shown as a card | same |
| send_message | simulated: shown as an "outbox" card, "nothing was sent" | same |

Downloads this needs (all free, no account): WordNet data, 5 opus-mt models (~1.5 GB), the Simple English Wikipedia
dump (a few hundred MB; exact size to check). Unit tests `temp/test_tools_exec.py`: >= 10 cases per tool, run offline on CPU.

### D3. Tool loop and the answer from the result (points 2-3)

One tool call per turn (the model has no training for chains; the page says so).
1. Prompt = tools block + history + question -> constrained decode (v2 grammar).
2. `ANSWER ...` -> shown. `TOOL say {json}` -> the sentence is shown, the executor runs, a tool card appears.
3. Second pass, **in the ordinary instruction format the trainer already supports, no new syntax**:
```
### Instruction:
{the user's question}

### Input:
Result from calculator: 40.8

### Response:
17% of 240 is 40.8.
```
- Data: new `scripts/gen_toolresult_data.py` -> `training_data/posttrain/toolresult.jsonl`, plain
  `{instruction, input, output}` records, which `train_sft.load_sft_corpus` (`src/train_sft.py:157`) already reads.
  For ~1,000 held-in tool records per tool: run the REAL executor (search against the offline pack, so results look
  like demo results; weather / time from sampled realistic values), then the Llama-3.2-3B teacher (already on disk,
  5080) writes a one-to-two sentence reply "using only this result". ~15% of search examples get an empty result and
  the reply "I could not find that." Automatic filter: the reply must contain the result's key value. ~9k examples,
  ~1.5 h of teacher time.
- First, as the "before" number: the same second pass with NO training on `sft_v4_reh13` (backlog idea 2).
- Eval `scripts/toolresult_eval.py`: on held-out records, faithfulness = share of replies that contain the result's
  key value; and an end-to-end score on 100 scripted questions (right tool, right arguments, executor ok, reply
  contains the value).

### D4. "Knows what it does not know" (point 1)

Port of **R-Tuning** (refusal-aware instruction tuning): label each training question by whether THIS model answers it
correctly, then train the behaviour.
- Pool: the 6,400 answerable (science questions with gold short answers) and 9,600 unanswerable questions already in
  `training_data/posttrain/abstain.jsonl`.
- Probe, new `scripts/selfknow_probe.py`, run on the checkpoint the SFT starts from: 4-shot "Question: / Answer:"
  prompt, the gold answer teacher-forced; **known** = every gold token is the model's top choice; **unknown** = the
  first gold token is not in the top 5; the band between is left out. One batched forward per question (minutes).
- Records (written as tool records, so they use the D1 path), new `training_data/posttrain/selfknow_<run>.jsonl`:
  known -> `ANSWER <gold>` (search is in the offered list 70% of the time, so the model learns not to search for
  what it knows); unknown + search offered -> `TOOL I will look that up for you. {"name": "search", "arguments":
  {"query": "<the question without the question mark>"}}`; unknown + search not offered -> `ANSWER I don't know.`
  (5 wordings that `scripts/abstain_eval.py:39` already recognises). Capped at ~12k records, both directions balanced.
- The labels belong to one checkpoint: the probe is re-run on the dense-final checkpoint (for SFT-A) and on the
  converted checkpoint (for SFT-B); it is one command in the SFT driver.
- Eval, new `scripts/selfknow_eval.py`, on held-out questions: "really known" is measured on the SFT model itself with
  the answer mode forced by the grammar. selectivity = P(search | really unknown) - P(search | really known).
  Always-search and never-search both score 0.
- **Honest failure mode, checked first at 13L and on the first 1B checkpoints:** if the model knows very few of the
  answerable questions (< ~10%), the behaviour collapses into "search every factual question". Then the page says
  "routes by question type" and does not claim self-knowledge.
- Confidence gauge (shown, never used to override the model): the existing `src/heads.py` ScalarHead on the last
  prompt position of the frozen SFT model, trained by `src/train_heads.py` on the model's own right / wrong labels.
  Shown only if it separates right from wrong (AUROC >= 0.75 on held-out). ~1 h on the 5080 after the SFT.

### D5. Multi-turn chat (point 3)

- Layout of one prompt: tools block once, then the turns; earlier replies are rendered as `ANSWER <final text>` (for a
  tool turn, the final reply from D3; the call and the result are dropped), then the new `### Instruction:`. Since the
  end marker is `\n###`, a transcript is a natural continuation of the trained format.
- Budget: the whole prompt is cut to 512 tokens (the SFT length): tools ~190, question ~60, the rest (~250 tokens,
  2-3 short turns) is history, oldest turn dropped first. The page marks which turns are still "in view".
- Data, new `scripts/gen_multiturn_data.py` -> `training_data/posttrain/multiturn.jsonl` (~10k), records
  `{history: [{q, a}], instruction, tools, target_mode, ...}`. Half is built by rule from existing tool records
  (same tool with a new argument "And in Tokyo?", unit switch, "double that" using the previous result), so the gold
  call is exact; half are teacher-written follow-ups with a pronoun or reference to turn 1. `tool_data.format_prompt`
  (:84) gets an optional `history` (absent = identical).
- Eval `scripts/multiturn_eval.py`: correct tool + arguments on held-out follow-ups WITH history vs the same follow-up
  WITHOUT history. The gap is the proof that history is used; if the no-history score is not low, the test set is too
  easy and is rebuilt.
- The "can a brain carry the chat" question: not with this model (plain-language cross-chunk recall ~chance). Carried
  by attention, and labelled that way.

  (`temp/energy_eval_v2.py`: weight reads, compute only, + SRAM fetch, + DRAM fetch), shown as three bars with the

- New endpoints / panels: tool loop with cards (D2-D3), history window (D5), brain selector and quiz (D7), an
  "offline" switch (forces every executor's offline path), the key-value memory showcase with memory-off replay
  (facts in the trained key-value format, > 1,024 tokens of filler, question; 100% vs ~16% at 13L).
- **Speed (target >= 15 tok/s at <= 512 tokens of context on the 5090, 1B; today 6-8):**
  1. `torch.compile` the inference forward at fixed lengths 128 / 256 / 512 / 1,024; the context is right-padded to
     the next length and the logits are read at the last real position (every layer is causal, so padding cannot

  2. `SpikeCode` statistics only when the brain view needs them: an attribute `stats` (default True = unchanged) in

  3. Only if 1-2 miss the target: trace every 2nd token, or a KV cache for RC3 (needs canon state + chunk restarts:

  Tracing (raster, meter) runs the eager path for the traced token; the page reports the measured tok/s.
- Reliability: `scripts/demo/run_through.py` drives the server through the 8 rehearsed scenarios and checks each
  expected tool / card / reply; the demo is ready when it passes 3 times in a row, online and offline.

### D7. Brains: read documents, train weights (point 5)

**What a brain is here:** a small adapter file (LoRA, the existing `src/lora.py`) trained on the frozen SFT model from
a document set, loaded and unloaded in about a second by adding its low-rank update into the base weights (the server
keeps the original matrices to restore them). Nothing is wrapped at inference time, so the sparse spiking operation,
the energy meter and the compiled forward are unchanged. At 1B, rank 32 on `qkv`, `o_proj` and `ffn` of the 12
attention blocks = 15.7M parameters = ~31 MB in 16-bit, about 1.4% of the model.

**Honest positioning:** adapters are a standard technique; any transformer can have them. What the demo can show
that is ours: the brain keeps the spiking / energy numbers (measured with the brain on), it is combined with the
"knows what it does not know" behaviour (brain off: "I will look that up for you"; brain on: it answers), and the
quiz has controls (wrong brain, facts never taught). The original idea, a brain as a memory file with no weight
training, stays unproven for plain language and is not shown.

**Pipeline** (research: training on the raw documents alone gives almost no closed-book gain; many differently worded
versions of each fact is what works: Ovadia 2023, Mecklenburg 2024, Yang 2024):
1. Read: new `scripts/brain_study.py` splits the documents into passages; the teacher lists the atomic facts of each
   passage.
2. Study material: per fact, 8 question / answer pairs in different wordings + 2 restatements, in the model's own
   format (`ANSWER <short answer>`, search offered 70% of the time). Separately written: 2 quiz questions per fact
   that are never trained on. Plus a control set of facts from held-out passages that are never taught.
   -> `training_data/brains/<name>/{study,quiz,control}.jsonl`.
3. Train: `src/train_sft.py` with `lora_enabled: true`, `lora_targets: [qkv, o_proj, ffn]`, r 32, alpha 64, AdamW
   lr 2e-4, `sft_max_len: 256`, study data + 20% replay from the general blend (so tools and format survive),
   3-10 passes depending on size, budget <= 4M tokens per brain. Output = the adapter file `train_sft` already writes
   (`src/train_sft.py:235`).
4. Serve: server endpoint `POST /brain {name | none}` merges / restores the weights.

**Mechanism test first, at 13L, before any real domain** (build step 6): 200 invented facts about invented entities
(templates, no teacher), same pipeline, on `sft_v4_reh13`. It answers: does knowledge injection by adapter work on
this architecture at all, does tool calling survive, do the energy numbers hold. If the quiz gain is < 20 points at
13L, try rank 64 and the memory-layer + Engram tables as targets before dropping the feature to "knowledge pack
behind search".

**Quiz, fixed in advance** (per brain, n >= 200 quiz questions, closed book, no tools offered):
base (no brain) vs brain ON vs WRONG brain ON vs control facts with the brain ON, and, for honesty, the search tool
over the same documents (expected to score higher: retrieval usually beats adapters in the literature, and the page
will say so). Shown as a bar chart on the page.

**Stretch, only if everything else is done:** build a tiny brain live (one page -> teacher writes the study material
-> a few minutes of training in the background -> quiz). Cut first if time is short.

Known ways these numbers could mislead, and the guard: quiz questions leaking into study data (split by fact, exact /
near-duplicate check); "self-knowledge" that is really question type (the forced-answer measurement); follow-ups
answerable without history (the no-history control); a brain that only memorised wording (quiz wordings never
trained; control facts).

- **Brains do not take at this scale.** Measured at step 6 before any domain work.
- **Five features in six days.** Cut order, last first: live brain building, confidence gauge, multi-turn, third and

- **Home-GPU contention with Glenn's use of the 5080:** he announces ahead; 5080 jobs are all resumable or short.
- **Network at demo time:** every live executor has an offline path and the offline switch is rehearsed.

## 7. Brain domains: Glenn chooses

What makes a good demo domain: the base model cannot know it (so off vs on is unmistakable), answers are short and
checkable, documents are free to use, the corpus is small enough to train in ~1 h, and it maps to a market where a
small private offline model matters.

| # | domain | why | cost / caveat |
|---|---|---|---|
| 1 | **Our own company and product (private documents)** | the model cannot know it, so the proof is clean; it is the enterprise pitch (your knowledge, on your device); personal for the audience | needs 5-20 pages of facts: Glenn supplies them, or I draft from the project docs for his edit |
| 2 | **One machine's manual (field service)** | model-specific numbers, error codes and procedures the base cannot know; offline technicians are a real market; the search found no small-model demo in this niche | manuals are the maker's copyright (fine for a private demo); candidate sets: TechManualQA-700 (20 manuals, CC-BY 4.0), Agri-Query (one 165-page manual, 108 questions, half unanswerable); availability to verify at build |
| 3 | **First aid / emergency response** | strongest "works with no network" story; a public set exists (FirstAidQA, 5,500 pairs, checked by medical professionals); others have shown demand (Nova F-R, Pocket RAG) | less novel; needs a "not medical advice" line; the base may half-know common items; dataset licence to verify |
| 4 | **Aviation (FAA Pilot's Handbook)** | US-government text, exam-style questions, tangible and impressive | the largest corpus (hundreds of pages): the most teacher and training time; third-party images / reprints need a check |

Recommendation: **1 and 2** as the two demo brains (cleanest proof + clearest market), **3** as the third if time
allows. 4 is the most work for the same point.
