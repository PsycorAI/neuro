1. The comparison model (v4 vs v4f)

  1. current v4f is a standard Llama-style transformer (RMSNorm, RoPE, QK-norm, SwiGLU, full causal attention) with the same parameter count as v4 (1,109M), trained on the same data, tokenizer, seed, token budget, optimizer family, Llama-3.2-1B distillation teacher and checkpoint averaging. n69 memory; configs/v4std_dense.yaml
  2. MUST The training recipe was developed for v4 (“home-field advantage”); v4f received its own learning-rate and warm-up check but no wider tuning. n69, Glenn decisions 10-19
  3. current Training differences: v4 was trained on a cloud H200, v4f on an RTX 5090 with gradient accumulation; v4's distillation phase drew its key-value recall tasks as 2 × 8 per step, v4f's as 1 × 16. n69
  4. pending One training seed per 1B model; seed noise is estimated from the 150M pair (two seeds each, ~2.7% spread). n67, n69 fairness to-dos
  5. MUST pending Quality: at matched training steps v4f has lower perplexity than v4 (e.g. step 144k: 29.98 vs 34.82); v4's advantages are energy, constant memory and the memory layer, not raw text quality. Final numbers after both post-trainings. n76 (temp/n76_valcurve.py)
  6. MUST Our 32k vocabulary maps rare Llama-3 tokens to an unknown token (17.2% of LAMBADA targets contain one), so absolute benchmark scores are not comparable with public models; v4 and v4f share the vocabulary, so their comparison is fair. n74/n75
  7. pending Any model-as-judge comparison names the judge (Claude), randomises answer order and is blinded. n77 review pass 2 (h)
  8. MUST Post-training used identical settings for both models, including v4's fine-tuning learning rate, which was chosen on v4 (out of two tried); v4f was not given its own learning-rate search. Glenn 10-26
  9. current Brains (LoRA add-ons merged into the weights) are not a spiking-specific advantage: v4f can carry brains the same way, and v4f receives the same post-training pipeline. n73, Glenn 10-22

2. Measured GPU energy (the Demo tab and the 5080 table)

  1. current Measured with the GPU's own power sensor (NVML instant power, sampled every 20 ms in a separate process), shifted 0.095 s for the sensor's measured reporting delay, integrated over the work; cross-checked against a wall-plug meter (wall / sensor 1.04–1.10 = the power supply). The card's energy counter reads ~0.8× and is reported only as a secondary figure. n78, n79, n80; gpu_meter.py, temp/n78_power_sampler.py
  2. current Totals include the GPU's idle power; idle-subtracted (“active”) figures are also given, since subtracting idle favours the slower model. n77 W1
  3. MUST The table is single-user (batch-1) decoding, one word at a time — the personal / edge setting. v4's sparse weight reads are a batch-1 effect: with many users batched together the rows needed grow, and a transformer server amortises its weight reads across users. n78 open item (5)
  4. current Both models run equally engineered: KV / state caching, CUDA graphs, and the decode step compiled (fused) with torch.compile. v4f's decode attention calls cuDNN, the fastest kernel for its masked one-word step (the one PyTorch had picked by itself in the first 5080 table); since 10-26 it is called directly, because PyTorch's own pick inside the compiled step varied by card and run (the 5090 got the mem-efficient kernel: its whole decode step ~4× slower at 32k). v4 makes no such call (its top-16 attention is plain matrix products). Parity: same logits as before within bf16 rounding (temp/n81_v4f_check.py). n81 (logs/n81_check.log) n80 (logs/n80_prof.log, n80_5090m.log) n79 (logs/n79_fuse_v4f.log sessions a/b)
  5. MUST v4-only optimisation: v4 reads only the weight rows of its exactly-zero (silent) inputs — exact, and a property of the architecture. v4f measured with standard dense inference; approximate activation-sparsity methods (e.g. TEAL) could narrow the short-context gap; applied to neither model. Also not applied to v4f: grouped-query attention, sliding-window / compressed KV cache, KV quantisation (each a v4f counterpart to v4's bounded state). Glenn 10-26; demo plan v2 fairness rule (ii)
  6. current Correction (10-26): the demo's “this conversation so far” bar priced v4's prompt reads with its graph-captured read but v4f's with its slower eager prefill (~2× dearer at 143–199 tokens), which favoured v4; both are now priced graph-captured (eager vs eager on a card without graph rows). n81 (scripts/demo/index.html cumAdd)
  7. current Long-session energy (10-26, measured, RTX 5080): one 16k-token session (89 turns), both models keeping the whole history, identical text for both (fixed reference replies go into the history; each turn's 48-word reply is decoded and measured as a side branch). v4 ~32 J per turn flat (546–553 mJ per word written); v4f 42 → 60 J per turn (833 → 1,168 mJ per word) as the session grows; session total 2,829 vs 4,563 J (v4 38% less). v4 reads prompts dearer (~32 vs 12–24 mJ per token: its read is not compiled; neither is v4f's). Caveats: (1) a transformer can also use a sliding attention window, which would keep its cost per word flat too (v4 would then still be ~1/3 cheaper per word from its sparse feed-forward layers, but the growing-gap story would go); (2) v4f was trained on 2,048-token texts, so its answers past that are out of its training range; (3) Glenn's idle demo server shared the card (same for both runs). n82 (temp/n82_long_session.py, logs/n82_long_full.log, docs/n82_long_session.png)
  8. must Long-session MEMORY (10-26): in the same run v4 recalled 5 planted facts right after they were said (5/5 as a plain-text cue, 4/5 asked in chat) but 0/5 once ~1,100 tokens of other text had passed — i.e. once the facts left its 1,024-token attention window; its spiking memory layer did not carry them, out to 16k. v4f (full attention) recalled 5/5 at 1,100 tokens and 0/5 from 2,048 on (past its training length). So no “remembers the whole conversation” claim for v4 today. Diagnosis (n82_mem_diag): turning the memory layer off changes no natural-language recall at any distance; it carries only the synthetic key/value pairs it was trained on (the demo's memory test). The demo's memory test must not be described as remembering what the user says. The chat-format recall test is also out of format for both (single-turn SFT; the v4f chat SFT is an early one). n82 (logs/n82_long_full.log)
  9. current Long-memory pilot (10-27, n83, NOT in the demo): a memory-layer-only fine-tune of v4 on 4,096-token sessions (facts, other text, questions). Best arm (n83_lm_mem_lr3): on held-out fact types it recalls 4/5 of the n82 facts from 1,000 to 4,000 tokens back and 3/5 at 6,000–8,000 (was 0/5), but only 1/5 of a second held-out set past 2,000; ~75–85% on the trained fact types. Matching is lenient (the word must appear: “Clara Barton” and “Biscuits” count). Small samples (5 facts per set); not “remembers anything you say”. Memory switched off: 0/5, so the recall is the memory's. Fairness: v4 trained only its memory block (85M params); v4f's matching run (same data, same length) will train its whole network, which favours v4f. n83 (docs/n83_long_memory_pilot.md, logs/n83_eval_n83_lm_mem.log)

3. Estimated energy on event-driven hardware (the Future-hardware tab)

  1. MUST An estimate for neuromorphic hardware, not a measurement. Figures: 45 nm (Horowitz, ISSCC 2014); int8 arithmetic is assumed (weights measured at int8 with no quality change; int8 activations not measured).
  2. MUST The headline includes reading weights from memory, which is where nearly all the energy goes; computation alone (~1% of the total) is shown separately and is not the headline — the standard critique of spiking-network energy claims (Yan et al. 2024; Dampfhoffer et al.; STEP). n77 (b)
  3. current The attention cache and the memory state are charged as on-chip reads in both models; the comparison is against v4f computed densely on the same hardware model, not v4 against itself.
  4. current Lowering energy further by coarser spikes or pruning costs perplexity; we chose not to trade quality for energy. Glenn 10-15 (n63)

4. Memory and recall claims

  1. MUST psycor.ai says “in our 350M model, zeroing the memory nearly doubles perplexity”. That was the older 363M model. Measured on v4 10-27 (temp/n84_memoff_ppl.py, logs/n84_memoff.log; bf16 weights, 100 val windows of 2,048): zeroing the memory raises perplexity only ~3% (base 16.34 → 16.78; chat 17.85 → 18.39; long-memory pilot 17.63 → 18.19), ~1% in the first 1,024 tokens and ~5% after. Do not apply the website claim to v4. State brain files (10-27, n84, test only, not in the demo): a 16.6 MB saved memory state brings 3/5 held-out facts into a fresh session (0/5 without), but the recall comes from block 6's 64-slot episodic cache (HOLA, softmax-read stored vectors), not from the Hebbian synapse matrix (0/5 alone); it fades after ~2k new tokens, and merging two brain files does not work yet. v4 is 12 attention blocks + one Hebbian memory block, and its demo brains are LoRA adapters, not saved memory states. n84 (docs/n84_vision_plan_2026_10_27.md)
  2. MUST v4's recall beyond its attention window (100% to 15k tokens) holds for the trained key–value format only; plain-language facts beyond the window are recalled at about chance. The demo's memory test uses that trained format (token pairs shown as words) and says so. n77 (a), n70, logs/n58_battery.log
  3. current At inference v4 uses a sliding 1,024-token attention window (trained with aligned chunks); this recovered plain-language facts inside the window (across a chunk edge 10% → 95%). Beyond the window, older text reaches the model only through its memory, which keeps the gist, not exact wording. n77, n78
  4. current Copying text from beyond the window is weaker and sensitive to numeric precision (bf16 vs fp32), in every decoding path. n78 finding 2, n79 re-check
  5. pending Plain-language recall at 0.5k / 1.5k / 3k / 8k for v4, v4f (full) and v4f (windowed) — v4f likely wins at 1–2k. To measure. n77 (a)
  6. pending Psyfile v2 (10-27, proposed, not built): if Psyfiles are described as “brain files”, say that the exact record is the text diary; the neural parts (fast-state cache, personal adapter) are rebuildable, model-specific caches. Psyfile parts that are known from others (verbatim memory, self-study into adapters, MemOS memory types, MacPaw Portable Memory) must be credited, not claimed. n84 (docs/n84_psyfile_design_2026_10_27.md)
  7. pending Psymem (10-27 brainstorm, not built): do not call it a “truly neuromorphic / synaptic memory” unless measured tests show the synapses do the recall work (v4's Hebbian M recalled 0/5 held-out facts on 10-27). Hebbian / associative memory for LLM agents is published (HeLa-Mem, ACL 2026; also HippoRAG, Larimar, Letta sleep-time compute) and must be credited. Memory benchmark numbers in this field are mostly vendor self-reports with different metrics; compare like with like. “PsyMem” is an existing 2026 paper name. n84 (docs/n84_psymem_2026_10_27.md)
  8. pending Memory benchmark method (psymem/bench.py, 10-27): items = single dialogue turns; embedder input truncated at 512 tokens (long LongMemEval assistant turns are cut); LoCoMo categories read as 1 multi-hop, 2 temporal, 3 open-domain, 4 single-hop, 5 adversarial; LoCoMo evidence ids not found in the conversation are dropped; abstention questions are scored separately, not in retrieval recall. Baselines and Psymem use the same embedder (bge-small-en-v1.5), so only the memory mechanism differs; a stronger embedder would raise both. n84 (docs/n84_memory_product_plan_2026_10_27.md)
  9. pending Psymem v0 method (psymem/core.py, 10-27 n85): (1) the lexical cue synapses reproduce BM25 weights by construction (saturation + heterosynaptic IDF + postsynaptic length normalization), so that channel alone is not a new retrieval method; (2) “ordinary search” includes two stronger baselines we added ourselves: hybrid_cc (the same divisive-normalized sum Psymem uses, on exact BM25 + exact cosine; beats RRF hybrid by ~5 r@10 on LoCoMo) and hybrid_cc_nb (plus neighbour-turn expansion), so Psymem's gains from S↔S neighbour links are priced against an ordinary system that also has them; (3) settings were explored on both LoCoMo and LongMemEval-S, so current numbers are DEV numbers; final claims need a held-out split and several seeds (FlyHash seed alone moves LoCoMo r@10 by ~0.6); (4) time cells use a hand-written English time-expression parser (when()); LoCoMo has no question date, so “now” = the last session date; (5) who cells take the speaker from the turn prefix; (6) learn-with-use feedback is simulated from gold evidence labels and tested on Llama-3.2-3B paraphrases (easier than truly new questions); (7) end-to-end QA uses a small local reader (Llama-3.2-3B) and judge (Phi-3.5-mini), so absolute scores are far below vendor GPT-4-class numbers — only relative comparisons hold. On LongMemEval-S (10-27, fly_k 128) Psymem r@10 84.5 vs hybrid 86.9 / hybrid_cc 87.6: the synaptic index lost to plain vector search there (vision-drift flag raised). n85
  • pending Plasmem demo v1 (scripts/memdemo, 10-27 n85): (1) the front end is bge-small, a transformer, shown on the page as “spiking encoder in training”; everything after it is synaptic; (2) the diary is invented by us (no benchmark data); tour questions were picked after checking that they show each mechanism (temp/n85_memdemo_probe*.py), so they are chosen examples, not a score; (3) who cells are a demo toggle (gain 0.5) and are not in the benchmark config; on this diary they rarely change a ranking, so “Who” is not a tour step; (4) confidence (10-27 night: coverage × the IDF share of the question’s words that have a word neuron; best Psymem signal on both benchmarks, AUROC LoCoMo 60.4 / LME 72.9 vs dense top-cosine 53.7 / 76.6, logs/n85_abstain2.log) is shown as experimental with a “weak: may never have been stored” band below 0.15; on 36 demo-diary questions we wrote ourselves it separates at AUROC 89.7, a biased, easy set; no abstention claim is made; (5) “meaning neurons fired” is fixed by k-WTA (4,096 of 65,536 = 6.25%); (6) no energy is claimed for this path; (7) benchmark numbers in the footer are dev numbers (see the Psymem v0 entry above). n85

5. Numerics and reproducibility

  1. current v4's outputs can change at the last-bit level with kernel shapes (spike rounding and top-16 attention amplify floating-point noise), so token-for-token identity is not our parity test; equal teacher-forced perplexity is. The demo runs in bf16 (the training precision). n77, n78
  2. current Every speed change passes a parity check (same replies on the demo set or equal perplexity; skipping zero inputs is exact). demo plan v2 rule (iii)
  3. pending Release: configs, logs, code and checkpoints for both models. n69

6. The demo

  1. MUST A backend layer sits around the model and is always shown on the page in orange: it routes explicit requests to tools, repairs tool arguments the model mis-copied, gives fixed replies to small talk, gibberish and topics a brain was not taught, and copies spellings from tool results. n68, n70, n71
  2. current Brains are narrow: the health brain knows 150 raw foods; the Python brain knows the functions it was taught. A router switches on one brain per question. n70, n73
  3. current Tools use live data (search, weather, time); a 1B model still makes mistakes (examples seen: “a spider has 12 legs”; a wrong list-reversal function). n80
  4. current v4f comparison box: 100% of v4f's feed-forward neurons are active (nonzero) for every word, measured; 27–31% of them are below 1/1000 of the largest — these are what approximate methods like TEAL would skip. n80
  5. current The demo runs on one consumer GPU, single user.
  6. current A continued (resumed) saved session restores the conversation as text: the model reads the earlier turns as in a live session (only the last turns that fit its 512-token prompt), the brain view and energy figures of the earlier turns are not replayed, and the brain is the one selected now. This is the backend re-reading saved text, not the model remembering across sessions. n81
